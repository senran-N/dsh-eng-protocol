# 判官高错误率诊断（2026-10-21）

根因是调度和输出恢复形成了持续退化的循环。上一轮扩充判官的任务理解、证据和关系输出后，输出额度仍按卡数估算；截断后拆小批次又同时减少输出额度。这一实现缺陷由插件负责，不能仅归因于模型慢或用户的超时配置。

代码和复现测试确认了以下问题：

1. **输出与批次相互缩小。** 旧公式为 `700 + 230 × 卡数 + 160 × 需判断关系数`，没有关系的单卡仅 930 tokens，但任务理解、引用、相邻定义的关系判断仍有固定开销。截断被理解为卡太多，继而继续拆批和降低输出。
2. **恢复条件要求整轮成功。** 批量能力只有整轮没有失败、拆批或补查才增长；单卡退化后，几十次请求不可能同时在 20 秒内完成，导致长期无法恢复。
3. **没有延迟样本也提前杀掉请求。** 旧代码无样本时以剩余时限的 65% 结束首个请求并重试，可能丢掉一条即将完成的正常响应，且把这个主动中断当拥塞继续降低并发。
4. **截断丢弃已完成判断。** 一个 JSON 尾部没闭合，就把前面完整的卡片一起丢弃并重做。工具已经输出了部分有效结果，面板却只能显示检查未完成。
5. **工作量和窗口不匹配。** 大输入在单卡调用中反复发送，成功调用本身接近 7 秒，却要在 20 秒内完成几十条规则，故障被进一步放大。修复恢复循环后仍需观察大目录和慢服务的实际覆盖率。

本次修复：

- 每批使用路由的输出容量，初始 8192 tokens，拆批不再减小额度；服务商明确拒绝该额度时自适应降低。单卡仍截断时可以增加一次额度，不做无限重试。
- 从截断或超时流中恢复完整 JSON 条目；不补造尾部，不放宽状态、置信度和引用校验，只补查未完成部分。
- 每个装满且完整回答的批次都可以训练容量恢复，不再要求整轮同时成功。
- 未知延迟时保留完整剩余等待；有可用历史样本时才安排提前的无输出检测，持续流式输出可以继续到总时限。本地计时器不降低服务商并发。
- 日志增加 `judgeRevision: 2026-10-21-output-recovery`、每次尝试的 `maxTokens`、恢复条数和实际模型调用数；面板展示这些信息。总超时文案不再笼统声称模型没有回答。

新增的十个可靠性场景覆盖上述路径；前六个先在修改前复现失败，再验证修复。测试使用可控模型响应和延迟，证明恢复逻辑，不代表真实服务商的延迟或语义质量已经达标。完整回归还包含真实 Chromium 面板检查。
