# Skill 注入机制审计与调研

核验日期：2026-10-19。范围：当前工作树、相邻 `deepseek-harness` 源码、历史决策日志及一手资料。

下文“可复现的发现”保留修复前的探针与分析。随后已实施以下改进；前一轮 125 项测试之外补充了证据、指标与运行时回归测试，具体结果以本次验证记录为准。

## 已实施的改进

- 发现 1：保存按顺序排列的完整用户要求，交给判官按最新指令判断任务修订或切换；“继续”保留原任务条件，事件与请求载荷的同一条消息去重。
- 发现 2：移除用户、助手、工具结果、动作内容的多层字符前缀截断，保留全部多处编辑。仍有历史窗口（8 次工具、6 条检查、4 条失败），显式提供遗漏计数；未实现历史证据检索。未处理事件队列也不再因超过 240 条而丢弃。
- 发现 3：缺失、非数字、非有限或越界置信度均保留为未知且置信度为零，记录格式错误，不能生成普通提醒。
- 发现 4：只有同回合证据与模型行为都超过送达水位、置信度达标的后续判断才能结算。满足、仍需、处理中和不适用分列；不再把处理中或不适用计为完成。面板去除“照做”和因果效果暗示。
- 发现 5：常驻上下文包含全部已核对义务及完整引文，去掉六条上限和句中截断；入口描述及适用说明也完整保留。编译提示要求完整条件与例外，取消引文长度上限，编译版本升为 5，旧缓存需重编。
- 补充：判官缓存包含完整动作参数，防止同文件不同改动复用旧判断。上游输入容量错误单独分类为 `context-limit`，不重复请求相同输入，判断保留未知。

仍有限制：发现 6 的无显著事件普通步骤仍依赖心跳；判官真实模型的推荐准确度尚未通过任务集评估。超过上下文容量时，尚无证据检索或安全的分段结论归并，因此不能声称已具备无限历史判断能力。

验证结果：`npm test` 全部 140 项通过（原有 125 项 + 新增 15 项），包括真实 Chromium 面板验证；`git diff --check` 通过。新增测试中 11 项专门覆盖证据与指标，另 4 项验证继续任务的原生 skill 加载提醒、同文件改动的缓存隔离、格式异常可观测性及上下文超限的完整判官链路。此结果证明确定性逻辑与模拟模型链路，不代表真实辅助模型的任务集表现。

## 2026-10-20：超时、轨迹和决策理解补充

- 超时改为一次判断共享总时限，排队、重试、入口、展开与复核不再各自重置。按相近输入规模及并行波数学习完整判断耗时，短请求不能压低长请求时限。每次尝试记录排队、执行、阶段与判断摘要，区分队列、模型及总时限耗尽；已完成部分保留。该上限不包含宿主步骤中单独的首次目录等待与已有判断等待。
- 判官收到最近 24 条连续用户 / 助手 / 工具动作 / 结果事件，含实际编辑内容、稳定证据引用、调用 ID 和可获得的宿主 seq。历史窗口的遗漏数量明确给出，恢复会话也重建连续证据。
- 请求判官先说明目标、约束、阶段与剩余交付，并给各卡提供精确证据引用。不存在的引用、缺失引用文本或不匹配引文令该卡保持未知。兼容没有新增字段的旧响应，但面板显式显示未引用的判断；任务理解本身只是模型解释，不能当成正确性证明。
- 完整证据和当时的候选卡按内容哈希单独存储，决策日志保留索引、哈希与预览，面板可按需查看。接口隔离项目和会话，日志轮转清理无人引用的旧快照；这会在本机保存用户输入、源码与工具结果。
- 跟进轨迹实时写入不可变快照，后台启动保持运行中，完成通知与 `job_output` 回填最终状态，普通文件中的退出码文本不再误报失败；最新回复可更新。面板读取最新快照，统计窗口按 400 条决策计数，跟进记录不再挤占窗口，轮询也会检测同一条记录的状态变化。缓存判断显示来源，轨迹链接使用当前调用 ID。
- 新增 `tests/runtime-review.mjs` 13 项，并扩展真实 Chromium 检查任务理解、超时明细和完整证据展开。全套测试现为 153 项，模型语义正确率仍未通过真实任务集评估。

## 结论

插件已有运行中发现与投递能力，但可靠性还受三个环节制约：判官看到的任务与证据是否完整、加载提醒是否真的转化为 skill 激活、指标是否反映最终结果。继续增加触发点无法单独解决这些问题。

当前加载流程是：目录入口 → 判官推荐 → 主模型调用宿主 `skill` 工具 → 正文进入上下文 → 异步编译 → 义务卡与常驻要求。推荐本身不等于加载，更不等于遵守。

## 可复现的发现

### 1. “继续”会替换判官掌握的任务

位置：[events.js](../lib/events.js) 的 `lastUser` 与 [decide.js](../lib/decide.js) 的 `evidencePayload()`。

探针：通过 `SessionLedger.observe()` 先输入 `Migrate postgres and provide rollback instructions`，再输入 `Continue`，把 `summary()` 传入 `decisionPrompt()`。

结果：`ledger.user` 只剩 `Continue`，判官提示里没有原始的 rollback 要求。原请求可以仍在主模型历史中，但插件没有把它保留给辅助判官。

影响：后续 skill 适用性与完成判定可能丢失原始交付条件。新回合还会清空待加载集合；简短的继续指令并不必然代表旧任务结束。

建议：保留原始任务、追加约束、完成证据与明确的任务切换事件，供后续判断使用。不能仅凭新用户消息到来就把旧任务替换掉。

### 2. 多层前缀截断使完成证据不可见

位置：[events.js](../lib/events.js)、[decide.js](../lib/decide.js)、[cards.js](../lib/cards.js)。

当前链路包括：

| 内容 | 存储 / 传递限制 | 后果 |
| --- | --- | --- |
| 用户消息 | 2000 → 1800 字符 | 后半段约束可能消失 |
| 助手回答 | 1600 → 900 字符 | 长回答后半部分的结果、验证和报告不可见 |
| 工具输出 | 1200 → 300 字符 | 错误尾部、检查结论可能消失 |
| 动作摘录 | 3200 → 2400 字符 | 较长改动的后部不可见 |
| 常驻原文摘录 | 每条 240 字符 | 后置条件或例外可能消失 |

探针：将 `x` 重复 1100 次，末尾附 `VERIFIED_REPORT_AT_END`，作为回答交给 `decisionPrompt()`。结果：判官只收到 900 字符，标记不可见。

这是确定的信息丢失；判官是否因此误判仍取决于具体任务，不能把探针当成真实模型错误率。

### 3. 缺失置信度被默认补成可投递值

位置：[decide.js](../lib/decide.js) 的 `normalizeAssessments()`。

探针：输入 `{ cards: [{ id: 'skill_demo_entry', state: 'needed' }] }`，省略 `confidence`。

结果：归一化后置信度为 `0.7`，在默认 `minConfidence: 0.6` 下被选择投递。

影响：缺失字段被变成肯定依据，configured threshold 无法约束这种不完整回答。模型的自报置信度本身也没有经过本项目标注数据的校准。

建议：严格区分有效判断、缺失字段、未覆盖候选、调用失败；不完整回答应修复或保留为未知。阈值的有效性应由真实任务集验证。

### 4. “正在处理”可在没有新行为时计为 resolved

位置：[store.js](../lib/store.js) 的 `aggregate()`。

探针：先记录一次 `needed` 投递，再放入时间晚一秒的 `addressing: 0.1` 判断；两条记录的 `evidenceSeq` 与 `responseSeq` 完全相同。

结果：`followUp.live.resolved` 为 `1`。结算接受较晚的判断时间，且把 `addressing`、`satisfied`、`inapplicable` 合并为 resolved，不检查该结论的置信度。

这些状态可以说明“不再需要同样提醒”，不能直接解释为“义务已经完成”。当前 README 已说明这是代理指标，但汇总仍无法区分这些情况。

建议：分别统计开始处理、已有完成证据、不再适用、仍然缺失、无法确认；核实模型是否实际消费了提醒及产生后续行为。不能用时间较晚替代因果证据。

### 5. 常驻要求始终只保留前六条

位置：[cards.js](../lib/cards.js) 的 `STANDING_PER_SKILL` 与 `renderStanding()`。

探针：一个 skill 放入七条同优先级、已核对原文的义务。结果：常驻消息只有六条，第七条不可见。

这是明确的压缩取舍，并非第七条从运行图被删除；它仍可在匹配事件时被评估。风险在于原始 skill 正文被压缩后，常驻上下文不能代表完整要求。

建议：常驻内容围绕当前任务的适用义务与未完成事项生成；保留完整来源、覆盖范围与重新加载入口，避免固定按条数截断。

### 6. 普通中途编辑不会主动发现全新 skill

位置：[cards.js](../lib/cards.js) 的 `SKILL_ROUTE_TRIGGERS` 与 `candidateCards()`。

探针：只有一个未加载入口，没有待加载请求，输入普通 `edit` 触发及动作。结果：入口候选为空。

当前主动路由覆盖新回合、首次编辑、检查开始、依赖、调研、委派、失败、卡住、心跳与结束；不等于每个普通读取、普通命令和后续编辑都会重扫目录。待加载要求能跟到普通动作前，但这不解决从未发现的 skill。

建议：利用任务阶段或操作目标变化触发补查，并保留按步数兜底。需要对目录规模与等待时间做测量；不能用词法前几名截断重新制造跨语言漏检。

## 字符限制是否必要

控制上下文成本、时延和模型容量是合理目标；这些目标不要求静默删除判断依据。当前数值是代码常量，本轮未找到证明 900 / 300 字符足够覆盖任务证据的评测依据，也未找到其历史决策说明。

| 用途 | 建议 |
| --- | --- |
| UI 标题、日志预览、错误摘要 | 可以限制展示长度，保留可打开的完整来源 |
| 24000 字符编译分段 | 保留：它把全文切开处理，不删除后文；现有测试检查字符覆盖 |
| 去重 ID 容量、超时、并发上限 | 属于资源和生命周期控制，需要独立评估 |
| 决定 task / skill 适用性、是否完成的证据 | 取消多层固定前缀截断，完整原文保留为可检索来源 |
| 发给主模型的 skill 原文与适用要求 | 保留完整语义，特别是后置条件和例外，避免固定六条或句中截断 |

推荐结构：原始证据完整保留 → 按当前卡片选择相关证据 → 在模型实际容量内组包 → 超长时分段与检索 → 每条判断注明来源及覆盖范围。无法取得相关证据时保留未知，不能因摘要里没出现就推断原始任务没有完成。

“把所有历史在每次判断时完整重发”也需测量其时延、费用与准确率。目标是让判官能取得完整相关证据，并显式知道本次看到了什么；字符数不能作为证据完整性的替代指标。

## 已排除的疑点与验证边界

- 本地宿主 `packages/core/agent-loop/src/agent.ts` 中，`inject()` 写入 `next-step` 队列。运行循环在等待 `agent/turn-stopping` 返回后再次检查这个队列，所以结束钩子内的 `inject()` 能继续当前回合；没有证据要求把它换成 `steer()`。
- `inject()` 不会唤醒已经空闲的 driver；单次流式请求也不会因消息入队而在中途重组上下文。这里的结论仅针对检查到的 DSH 实现。
- 最后一次访问原桌面端口 `42376` 被拒绝，随后未发现名称匹配的 DSH 桌面进程。本轮不能继续确认在线实例的加载版本；此前“旧版本仍在线”的判断不能作为本轮实时状态。
- 历史 `decisions.jsonl` 共 1330 条 decision，其中 527 条含 skill 候选，4 条记录投递 skill；最近 200 条中分别为 194 和 0，这 200 条没有判官错误或超时。这是混合历史版本的观测，不是修复版召回率；缺少人工标签，不能由候选数推断本来应该投递多少次。

## 调研对照

- OpenAI 官方文档说明，skill 先暴露名称与描述，再按需加载完整正文。这支持区分“推荐”和“激活”，不能将加载提醒当作激活成功。见 [Build skills](https://learn.chatgpt.com/docs/build-skills)。
- Agent Skills 集成文档把激活定义为完整指令进入上下文，并讨论长期保留及压缩保护。仅保留六句摘录不能证明压缩后的 skill 语义完整。见 [Adding skills support](https://agentskills.io/client-implementation/adding-skills-support)。
- Anthropic 建议按需获取相关上下文、压缩时保留关键决策和未解决事项。由此推导，本插件应提供证据检索与覆盖信息，而不是多次截取前缀。见 [Effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)。
- OpenAI 建议用真实任务分布评估，并用人工反馈校准自动评分；Anthropic 区分轨迹和环境最终状态。这支持对判官与结果分别验收。见 [Evaluation best practices](https://developers.openai.com/api/docs/guides/evaluation-best-practices)、[Demystifying evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)。
- Agent Skills 建议同任务分别有 / 无 skill 运行，以产物和时间、token 成本作对照。见 [Evaluating skill output quality](https://agentskills.io/skill-creation/evaluating-skills)。
- 2023 年 [Lost in the Middle](https://arxiv.org/abs/2307.03172) 证明其测试模型在特定长上下文检索任务上受信息位置影响。它提供测试动机，不能直接推算当前 DeepSeek 模型在本插件里的错误率，更不能推出 900 字符是合理阈值。

## 建议的实施与验收顺序

1. 保留任务及完整证据，消除多层有损截断；增加“继续”、证据在末尾、条件跨段、检查输出很长等回归案例。
2. 验证判官输出完整性，拆开状态指标与时间归因，避免把无依据的自报值当完成证据。
3. 明确记录候选、判断、推荐送达、原生加载成功、编译、义务送达、最终产物七个阶段，并记录来源版本，定位具体在哪一步断开。
4. 以真实失败起步建立小型评测集，覆盖应加载、不应加载、继续任务、压缩后遗忘、运行中目标变化等正反例；固定宿主版本、目录和任务输入，对照关闭插件 / 旧版 / 新版，多次运行并核验真实产物。

验收至少分别报告：适用 skill 的发现率、无关推荐率、成功加载率、首次提醒距离错误动作的步数、义务完成率、误拦截率、阻断等待时间及模型调用成本。假宿主链路测试与真实模型效果评测分别报告，不能用前者的通过数量替代后者。
